## 多实体分桶图 JSON 自动展开接入（方案 B）

**背景**：用户上传 `automotive_embedded_ontology_all_data.json`（汽车网关 ECU 本体导出，
82 KB）时「解析不了数据源」。诊断结论：该文件顶层是
`{ metadata, objects: { 18 个实体桶 }, relationships: [195 条] }`，而行提取口径只认
数组 / `items` / `rows` / `results` / `data`，不认 `objects` → 落到单对象兜底，
整个文件被读成 **1 行 × 3 列**（metadata / objects / relationships），实体识别与列映射全空。
且只在「0 行」或「0 列」时才抛错，所以是**静默失败**（预览能进、接入后只有一条垃圾行）。

**实现**

1. `src/lib/jsonAutoImport.ts`
   - 新增判别联合：`AutoImportResult`（加 `kind: 'flat'`）/ `GraphImportResult`（`kind: 'graph'`）。
   - `bucketContainerOf()`：认 `objects` / `entities` / `instances` / `nodes`（**故意不含 `data`**，
     避免抢走 GraphQL 包装语义）；要求容器内有数组值且至少一行是对象。
   - `matchEntityByBucketName()`：归一化后完全同名 6 分 / 包含 3 分（被匹配串更长者优先）。
   - `assignBucketEntities()`：按分降序贪心，**一个实体只被一个桶占用**；未命中的桶在
     **桶名「像实体名」时禁止退化成列名硬猜**（`looksLikeEntityName()`：长度 ≥5 且含大写或分隔符，
     通用容器词 `rows`/`data`/… 除外）——否则 `Test_Case` 会被 `status` 列误映射成 `order`。
   - `buildGraphResult()`：逐桶行/列/截断 + `relationships` 提取 + `metadata` 短字符串抽取。
   - `parseImportFile()` 成为唯一入口（一次 `JSON.parse` + 自动判别）；
     `parseJsonForImport()` 保留为扁平行专用薄封装（分桶图会让它抛可执行提示）。
2. `src/components/EndpointConnector.tsx`
   - `AutoImportState` 加 `graph` 分支（记 `hidden` 桶名 + `includeRelationships`）。
   - 新增桶列表 UI：逐桶勾选（行/列数 + 匹配实体）、全选/全不选、关系表开关、名称前缀输入、
     「N/M 个桶已匹配」；全部未匹配时给出「先导入对应本体」的提示。
   - `handleAutoConnectGraph()`：一个桶 = 一个数据源（`前缀 · 桶名`），关系表单独一个数据源；
     **同名原地 `updateEndpoint` 刷新**而非堆重复项。
   - 顺手修：`ENTITY_BY_ID` 写死 Fourth Coffee 本体 → 改为基于 `currentOntology` 的
     `entityById`（用户导入自己的本体后实体 chip 不再消失）。
3. `src/styles/app.css`：`.auto-import-meta` / `-stat` / `-buckets` / `-bucket` / `-relation`
   等样式 + `≤600px` 适配。

**验证**：`jsonAutoImport.test.ts` 25 → 40，`EndpointConnector.test.tsx` 13 → 17；
全量 **32 文件 / 631 测试全绿**，`tsc --noEmit`、`eslint`、`vite build` 均通过。
用真实文件实测：18 桶 / 91 行 / 195 条关系全部展开正确。

**文档**：README、TODO（新增 11.1 节）、`docs/default-data-sources.md`（新增分桶图小节）。

**待办**：用户在 Fourth Coffee 本体下 18 个桶全部「未匹配」——属于预期行为，
需先导入汽车本体后重新上传才能自动映射；后续可考虑「桶 → 实体」的手动绑定入口。

## 可行性咨询：让智能回答具备修改数据源的能力（2026-09-18 下午，仅评估未动工）
- 结论：**本地 JSON 文件数据源（`localRows`）可完整闭环**；REST / GraphQL / SPARQL 只能"发起写请求"，
  成功与否取决于远端是否开放写方法与鉴权（平台目前只发 GET，且浏览器直连有 CORS）。
  `needsFileReupload` 的恢复源无数据，不可写。
- 关键事实（已核对）：`src/lib/llmClient.ts` **无 tool/function calling**（全库搜不到 `tools`/`tool_calls`），
  只有纯流式 chat；`endpoints` **未持久化**（只 theme / llm / aiSystemPrompt 落 localStorage）；
  `AIQueryConsole` 有 `cacheRef`（TTL 60s）——写后必须失效，否则问答仍用旧行；
  `InstanceBrowser` 靠 `useEffect` 依赖 endpoints 抓取，需不可变更新触发。
- 建议分期：① 提示词意图协议 + 行/字段定位 + 追问状态机 + 确认后改 `localRows` + 失效缓存 + 修改日志（含撤销）；
  ② 日志面板 UI / 批量；③ 远端源写入（PATCH / mutation / SPARQL Update）。
- 安全底线：AI 只产变更提案（dry-run diff），**执行必须全在本地代码**，用户确认才落盘；模型不得自称"已修改"。

## 私有网关连不上（Failed to fetch）修复（2026-09-18 下午）
- 现象：用户自建网关 `https://api.qingcuicore.com/v1` + 模型 `gpt-5.6-sol`，报「请求被浏览器跨域策略拦截」。
- **实测根因**（不是配置问题）：`OPTIONS /v1/chat/completions` → **403 且无 `Access-Control-Allow-Origin`**；
  `POST` → 401 JSON（网关本体正常）但同样无 CORS 头 → 该网关（Caddy）**完全没开 CORS**。
  预检在响应到达 JS 之前被拒，前端拿不到状态码也**无法绕过**。项目此前只写了「填代理前缀」
  的提示，**却没有代理** —— 缺的是这一环。
- 新增 `scripts/llm-proxy.mjs`（零依赖，`npm run llm:proxy`，默认 `127.0.0.1:8787`）：
  OPTIONS→204 + 补 CORS（**回显 `Access-Control-Request-Headers`**）；转发 GET/POST/PUT/PATCH/DELETE；
  **SSE 逐段直通**（`accept-encoding: identity` + `x-accel-buffering: no` + `cache-control: no-cache`）；
  丢弃上游自带 CORS 头（避免重复值被浏览器判非法）；剥离 `origin`/`referer` 绕开防盗链；
  `/__health` 健康检查；`LLM_PROXY_ALLOW` 域名白名单；只绑回环、不存 Key。
  坑：`Readable.fromWeb` 被调两次会从同一 body 造两个流互抢 → 只造一个，`pipe` 直通。
- `llmClient.ts`：`llmErrorHint(code, { hasProxy })` 分流 —— 没配代理引导启动；
  **已配代理仍失败则矛头指向代理自身**（再让用户「去填代理」是答非所问）。
  新增 `probeProxy()`（打 `/__health`，一刀切开「代理没起」与「Key 不对」）、
  `normalizeProxyBase()`、`isMixedContentRisk()`（https 页面 + http 代理会被混合内容拦截，
  localhost/127.0.0.1 例外 → 本地开发不暴露、部署后才炸，必须提前警告）。
  同步把 AIQueryConsole 的错误提示也接上 `hasProxy`。
- `llmProviders.ts` 新增 `DEFAULT_LOCAL_PROXY_BASE = 'http://127.0.0.1:8787'`
  （用 127.0.0.1 而非 localhost：个别 Windows 解析成 IPv6 `::1` 而代理只监听 IPv4）。

## 代理配了仍连不上：从「修报错」到「不再发生」（2026-09-18 下午续）
- 用户报：已配代理仍提示「代理已配置但请求仍失败…网络请求失败」。

  且都带 `access-control-allow-origin`。所以是客户端侧问题。
- 三处根因（都在客户端）：
  1. **代理前缀漏写协议会静默失败**：`127.0.0.1:8787` 拼出非法绝对 URL、
     `localhost:8787` 被当成 scheme 为 `localhost:` 的地址 —— 都只抛 `Failed to fetch`。
     → `normalizeProxyBase` 补 `http://`；`withProxy` 复用同一份（原来两处各写一份）；
       新增 `proxyPrefixIssue`（协议 / 误带路径）在输入框下方当场提示。
  2. **失败提示没有信息量**：原提示只让用户「自己去点检测代理」。
     → 新增 `diagnoseProxyFailure`：先查写法（不碰网络）→ 再敲 `/__health` → 给确定结论。
       返回结构化结果（prefixIssue / reachable / probeMessage / probeElapsedMs / message），
       **一次探测两处复用**（AIQueryConsole 的 hint + 「检测代理」面板），避免结论打架。
       异步探测后重校验 `runIdRef`。
  3. **真根因是「代理没启动」** → `vite.config.ts` 新增 `llmCorsProxyPlugin`（`apply:'serve'`）：
     `npm run dev` 顺手拉起代理。**只在 `process.once('exit')` 回收**——
     若挂在 `server.httpServer` 的 close 上，vite 重启 dev server（改配置/.env）时会先杀子进程，
     新进程可能撞上未释放的端口而以「端口被占用」退出，结果重启后反而没有代理。

  （渲染出 `…:8787https://…`），显示的地址与真正请求的不是一回事。改为复用 `withProxy`。
  这个是靠新建的测试断言 URL 形状才暴露出来的。
